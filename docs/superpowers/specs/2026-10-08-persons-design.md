# The persons each eulogy names (editio altera 2004, Latin) — design

Date: 2026-10-08. Builds on `docs/superpowers/specs/2026-09-30-places-extraction-design.md`
and `docs/superpowers/specs/2026-10-01-gazetteer-design.md`, whose split between extraction
and identification, and whose review change-set, this follows.

## Goal

List the saints and blessed each eulogy commemorates, by name, with where the name is
printed (the text, or which footnote), and identify each with a Wikidata item where one
exists. The data feeds an index of names per edition in martyrology-frontend
(`/read/<edition>/names`, a later spec), where a name printed in the text links to the
eulogy and a name printed in a footnote links to that footnote.

The principle of the places work holds: **an unidentified person is better than a
misidentified one.** A person is identified only by strong, consistent evidence (`auto`) or
by a curator (`reviewed`).

## Scope

This is round 1 of four:
1. **This spec:** the Latin editio altera 2004 (`martyrologium_romanum_2004`): extraction,
   Wikidata matching, the review change-set, and the review card in martyrology-frontend.
2. martyrology-frontend: the index of names for the 2004 Latin, and the reader's handling of
   `#fn-…` links (its own spec).
3. The Italian and English 2004 editions: each name's position in those editions (the people
   are the same; only the footnote positions may differ).
4. The older editions (1630, 1749, 1914 English), whose texts and people differ.

In scope here:
- `scripts/extract_persons.py`, `data/persons.json`, `data/persons_curated.json`,
  `docs/persons-report.md`.
- `scripts/build_person_items.py`, `data/person_items.json`,
  `data/person_items_review.json`, `docs/person-items-report.md`.
- The `resolve_person` op of `crmedr-changeset/v1`, defined here so both repositories share
  it, and the review card for it in martyrology-frontend (a separate PR there).
- Tests and documentation (AGENTS.md, README).

Out of scope:
- Rounds 2–4.
- Proposing a "Roman Martyrology ID" property to Wikidata, or creating missing items there.
- A crmedr identifier scheme for persons (see Identity).

## Who is named

Only the **saints and blessed the eulogy commemorates**:
- the eulogy's subjects;
- the companions it names, in its text or in its footnote;
- the Blessed Virgin Mary, in her feasts and memorials.

Not listed:
- persons mentioned in passing: a teacher, a pope, a persecutor, a relative, the saint a
  church is dedicated to (*in basilica sancti Petri*);
- feasts of the Lord, which commemorate no person to index;
- anonymous groups (*Quadraginta milites*);
- unnamed companions: *Sanctus N. et socii* with no names given lists N. only.

## Identity

There is no new identifier scheme. A person's key, for the index, is their **Wikidata QID**
when identified, and otherwise their **headword** (the Latin nominative name). Two
unidentified namesakes share a heading until one is identified. Identification is decided
per eulogy and name: a bare *Ioannes* is a different person in every eulogy.

## Data

### `data/persons.json` (generated by `extract_persons.py`)

```json
{
  "$comment": "The saints and blessed each eulogy commemorates, by edition: the Latin nominative name (honorific-free) and where it is printed, the text or the eulogy's nth footnote. Generated by scripts/extract_persons.py; see docs/superpowers/specs/2026-10-08-persons-design.md. Draft pending committee review.",
  "editions": {
    "martyrologium_romanum_2004": {
      "mr:0206-paulus-miki-et-socii": [
        { "name": "Paulus Miki", "where": "text" },
        { "name": "Ioannes de Goto Soan", "where": { "footnote": 1 } }
      ]
    }
  }
}
```

- Eulogies in print order (month, day, entry); persons in the order printed, the text first.
- `where.footnote` is the footnote's 1-based position among the eulogy's footnotes, as the
  frontend numbers its anchors (`fn-<edition>-<id>-<n>`).
- Current IDs only. A eulogy that names no one (a feast of the Lord, an anonymous group) has
  no key.
- **No text is quoted.** Only the nominative name is stored, a fact, like the subjects in
  `i18n/la.json`. The forms as printed (often genitive) are used to check the names and are
  never written. AGENTS.md's rule that no eulogy text is stored stands unchanged.

### `data/persons_curated.json` (hand-entered)

Names the script cannot extract, by eulogy: `{id: [{name, where}]}`. The script takes them as
given, after the same checks, in place of what it would extract for that eulogy.

### `data/person_items.json` (identification decisions)

```json
{
  "$comment": "…",
  "statuses": ["auto", "reviewed", "unresolved"],
  "persons": {
    "mr:0206-paulus-miki-et-socii": {
      "Paulus Miki": { "wikidata": "Q380649", "status": "auto" },
      "Thomas Kozaki": { "wikidata": null, "status": "unresolved", "note": "No item on Wikidata (checked 2026-10)." }
    }
  }
}
```

- `auto`: exactly one candidate passed the evidence bar. `reviewed`: a curator chose it.
  `unresolved`: a curator found no item (`wikidata: null`, `note` required).
- A person with no key here is not yet decided: queued in the review change-set, or not
  processed.
- `propose` never changes or removes a key; a curator does, by editing the entry or deleting
  it and rerunning `propose`.

## Extraction: `scripts/extract_persons.py`

Standard library only. Reads `data/martyrology_ids.json`, `i18n/la.json`,
`data/persons_curated.json`, and from the private `martyrology-texts` the 2004 Latin texts
(`data/editions/martyrologium_romanum_2004/MM.json`) and footnotes (`footnotes.json`, with
`footnotes-overrides.json` applied as the API applies them). Writes `data/persons.json` and
`docs/persons-report.md`.

Run: `python3 scripts/extract_persons.py /path/to/martyrology-texts`

### 1. Subjects, from `i18n/la.json`

- A subject counts only if it opens with an honorific: *Sanctus, Sancta, Sancti, Sanctae,
  Beatus, Beata, Beati, Beatae*. Celebrations without one (feasts of the Lord, dedications)
  name no person. Celebrations that commemorate a saint without opening with an honorific
  (*Conversio Sancti Pauli Apostoli*, *Cathedra Sancti Petri Apostoli*, *Bonus Latro*) are
  listed in `FEAST_PERSONS`. Subjects that carry an honorific but name a group (*Sancti
  Innocentes*, *Sancti Quadraginta Milites Sebastes*) are listed in `GROUP_IDS` and name no
  person.
- Strip the honorific; split on ` et ` and `, `; drop *socii* / *sociae*.
- Marian subjects become one person, *Maria*, through `MARIAN_IDS` (a commented constant of
  the eulogies whose subject is the Blessed Virgin), never by splitting their subject.
- Hand decisions (a subject that splits wrongly, a title that is not a person) go in
  commented constants, following the repository's convention (`ID_CORRECTIONS` and the like).
- Every subject name is printed in the eulogy's text (in some case): `where: "text"`.

### 2. Footnote lists

All 70 footnotes of the 2004 Latin are lists of names, opening *Quorum nomina:*, *Quarum
nomina:* (with or without the accent) or *Inter quos:*.
- Take the text after the opening; split on `;` into groups and on `,` into segments.
- Drop an honorific at the head of a segment (*sancti, beati, sanctae, beatae*).
- A name is the run of words from the segment's start up to the first lowercase word that is
  not a name particle (`de, a, ab, van, von, di, da, du, la, le, y, dos, das, del`) followed by
  a capitalized word: *Ioannes Maria Gallot, presbyter* → *Ioannes Maria Gallot*; *Martinus ab
  Ascensione Aguirre* keeps *ab Ascensione*; *Thomas, eius filius* → *Thomas* (the segment
  *eius filius* has no name and is dropped).
- A segment with no capitalized start (*presbyteri ex Ordine…*, *catechistae*) is a
  descriptor of the group before it and is dropped.
- A footnote name equal to one of the eulogy's subjects is not added twice.
- `where: {"footnote": n}`.

### 3. Companions named in the text

For every *et socii* eulogy without a curated entry, footnote or not (a eulogy can name some
companions in its text and list the rest in its footnote), read the opening group of names in
the text: after the genitive plural honorific (*sanctorum, beatorum*,
optionally followed by *martyrum, virginum, …*), the names up to the first word that is not a
name, a particle, `,` or *et*. Convert each from the genitive to the nominative with a table
of genitive endings (`GENITIVE_ENDINGS` in `scripts/persons_text.py`); a form is converted only
when exactly one of its possible nominatives is a known name (the lexicon of the names in
`i18n/la.json`'s subjects and in the footnotes). A conversion with more than one possible nominative, or none,
is not written: it goes to the report as uncertain, for a curated entry. Names found here come
before the footnote's, and a name in both is listed once, as in the text.

### Checks (the script fails on any)

- Every footnote name appears verbatim, as whole words, in its footnote.
- Every name taken from the text was read from the eulogy's text (the printed form exists).
- Every subject name agrees with `i18n/la.json`.
- No name appears twice in one eulogy.
- Every key is a current ID; every `where.footnote` is within the eulogy's footnotes.
- Curated entries pass the same checks.

### Report: `docs/persons-report.md`

Counts (eulogies, persons, by where); *et socii* eulogies where no companion was found;
uncertain nominatives; footnote segments not parsed.

## Identification: `scripts/build_person_items.py`

Standard library only; uses `scripts/wikidata.py` (cached under `.cache/wikidata/`, with its
User-Agent, `maxlag` etiquette and retries). Subcommands mirror `build_gazetteer.py`.

### `propose` (network)

1. Collect each person in `persons.json` with no decision in `person_items.json`.
2. Find candidates (below) and test them against the evidence bar:
   - exactly one passes: write an `auto` entry;
   - otherwise: write a `resolve_person` op to `data/person_items_review.json`, with the
     ranked candidates and the rules that failed.
3. Never modify or remove an existing decision. Existing ops keep their `suggested`,
   `reasoning` and `confidence`; only their candidates are refreshed.
4. A person whose lookups fail is listed as not processed and left for the next run.
5. Write `docs/person-items-report.md`.

### Candidate search

- `wbsearchentities` for the name in `la`, `it` and `en`, and for the name without particles
  when it has any; the union of the hits.
- For each candidate: P31 (instance of), P411 (canonization status), labels and aliases in
  `la`, `it`, `en`, P569 / P570 (birth, death), P841 (feast day), the description.

### The evidence bar for `auto`

A candidate passes when all hold:
- P31 includes human (Q5);
- P411 is a status of saint or blessed (`SAINT_STATUSES`, a commented constant of the QIDs
  Wikidata uses: saint, Catholic saint, canonized saint, blessed, and the titles it gives ancient
  and Eastern saints instead: hieromartyr, Reverend Martyr, thaumaturge, pre-congregation saint,
  great martyr, passion bearer; not Venerable or Servant of God);
- a label or alias in `la`, `it` or `en` matches the name, compared folded (accents, case,
  `i`/`j`, `u`/`v`, `ae`/`æ`);
- when the eulogy's typology is `dies_natalis`: P570's month and day equal the eulogy's day, or,
  for a P570 known only to the month, its month equals the eulogy's month. A year alone fails:
  a eulogy has no year to check it against (decided 2026-10-09, after a sample of year-only
  matches named a famous namesake for a third of one-word names).

For other typologies there is no date to check; their `auto` matches are listed in
`docs/person-items-report.md` for a curator to scan (decided 2026-10-09), and a wrong one goes into
`FORCE_REVIEW`.

`auto` needs exactly one passing candidate. A wrong `auto` that no general rule catches goes
into `FORCE_REVIEW`, with a comment. A run stops asking after five persons in a row whose lookups
failed (Wikidata lagged), leaving the rest for the next run.

An item matched automatically in more than one eulogy through a one-word name is usually a famous
namesake (Augustine of Hippo had matched Augustine of Canterbury's days): none of those matches is
`auto`; they are queued with the reason shown (decided 2026-10-09, after the review of
CatholicOS/crmedr#79).

### `verify-suggestions` (network)

As for the gazetteer: Claude may fill `suggested: {wikidata}`, `reasoning` and `confidence`
(`high | medium | low`) in queued ops, in batches. This subcommand checks each suggestion: the
QID exists, is human and has a saint/blessed status; if it is not among the candidates it is
fetched and added, so the card shows its evidence. A suggestion never makes a person `auto`.

### `apply <exported change-set>` (offline, except for a QID not among the candidates)

- `accept` → `reviewed`, from `suggested` (or the top candidate when there is none);
- `edit` → `reviewed`, from `edited.wikidata` (fetched and checked: human, saint/blessed
  status);
- `reject` → `unresolved`, with `edited.reason` as `note` (required).

Decided ops leave the change-set; undecided ones stay. An op for a person already decided is
an error.

### `check` (offline)

Validates `person_items.json` against `persons.json` (every key is a person of the eulogy;
statuses and notes well formed) and the change-set against both.

## Review change-set: the `resolve_person` op

`data/person_items_review.json` is a `crmedr-changeset/v1` document
(`base: {edition: "martyrologium_romanum_2004", registry: "data/persons.json"}`):

```json
{
  "op": "resolve_person",
  "id": "mr:0206-paulus-miki-et-socii|Thomas Kozaki",
  "eulogy": "mr:0206-paulus-miki-et-socii",
  "day": "02-06",
  "typology": "dies_natalis",
  "subject": "Sancti Paulus Miki et socii",
  "name": "Thomas Kozaki",
  "where": { "footnote": 1 },
  "companions": ["Paulus Miki", "Ioannes de Goto Soan", "…"],
  "failed": ["name: no candidate's label or alias matches"],
  "candidates": [
    { "wikidata": "Q…", "label": "Thomas Kozaki", "description": "…",
      "statuses": ["Q43115"], "born": "1583", "died": "1597-02-05", "feast": ["Q…"],
      "evidence": ["human", "status", "name"] }
  ],
  "suggested": { "wikidata": "Q…" },
  "reasoning": "…",
  "confidence": "medium",
  "decision": null,
  "edited": null
}
```

`id` is `<eulogy>|<name>`, unique in the change-set. `decision` is `accept | edit | reject`;
`edited` carries `wikidata` (edit) or `reason` (reject).

## The review card (martyrology-frontend, separate PR)

`lib/changeset.ts` gains the `resolve_person` op type, adjudicable like `resolve_place`, and
its export. `components/PersonCard.tsx`, modelled on `PlaceCard`, shows the eulogy (ID, day,
subject, typology), the name and where it is printed, the companions, and the candidates as
choices (label, description, statuses, dates, feast, a Wikidata link, the evidence); a field
for another QID; and "No item" with a required reason. The suggestion, when there is one, is
preselected with its reasoning and confidence shown.

## Tests

crmedr (`unittest`, inline fixtures, no private texts):
- subjects: honorific stripping; pairs, lists and *et socii*; celebrations dropped; the
  Marian map;
- footnotes: the openings; groups and segments; honorifics; descriptors dropped; particles
  kept (*ab Ascensione Aguirre*); *Thomas, eius filius* → *Thomas*; no duplicate of a
  subject;
- companions in the text: the common declensions; an ambiguous form goes to the report;
- each check rejects a bad input;
- the evidence bar (each rule; a death date on another day blocks `auto`; two passing
  candidates queue); `apply` for accept, edit (checked QID) and reject (reason required);
  `propose` leaves decisions alone; Wikidata mocked through the client's cache, as in
  `test_gazetteer.py`.

martyrology-frontend (Vitest): the card renders an op, chooses a candidate, takes another QID,
requires a reason for "No item"; the export carries the decision.

## Rollout

1. crmedr PR: the extraction, `persons.json` and the report; the identification script, a
   first `propose` (with `auto` entries and the review change-set); tests; AGENTS.md and the
   README (pipeline steps 6 and 7, the new files, the rule that names are stored as facts).
2. martyrology-frontend PR: `resolve_person` and `PersonCard`.
3. Curators review; `apply` writes their decisions.

Then round 2, the index of names, has its data.
